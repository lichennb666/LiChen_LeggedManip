## Decisions Made
| 决策 | 理由 |
|----------|-----------|
| 将 `9387bf47…c579` 冻结为金标准 | 它已完成 4000-iter finetune，且在 Floor1 主线有多次导航抓取成功记录 |
| 当前优化对象首先定义为 Gazebo Classic/ODE Floor1 主线 | 用户描述的导航抓取任务与 `floor1_navigation.launch.py` 对应；DART 线尚未通过站立门禁，不能混用结论 |
| Classic 作为首轮主交付引擎，DART 暂缓 | Classic 已完成任务且 actor 原始速度测试达到约 0.505 m/s；DART 尚不能稳定站立，迁移成本与风险更高 |
| 部署侧诊断优先于再次训练 | Floor1 使用 `contact_trot_blend=1.0`，最终腿目标由四拍 IK 完全覆盖，视觉拖脚不能直接归因于 actor |
| 采用分场景 blend 而非一套参数覆盖全程 | 高速长距离、低速桌前对正、机械臂抓取和载物导航对步态的稳定裕量不同 |
| actor 原始输出与最终控制目标必须同时 trace | 只看 `/cmd_vel`、里程计或足端峰值无法定位覆盖层与接触层问题 |
| 完整导航抓取是每个候选的硬门禁 | 单纯行走更好但破坏低速站位、抓取稳定或载物导航不算成功 |
| 不直接执行已准备的 yaw 专项 finetune | 当前任务是前腿拖地且抓取必须保持；先确认 gait overlay 根因，避免引入额外变量 |
| 四拍动态候选改为 1.45 Hz、40% 摆动、15% 抬升/15% 落地、0.10 m 步长、0.075 m 抬脚 | Gazebo 动态测试表明 1.60 Hz、20%/20% 与 2 rad/s 目标限速带宽不足；新参数保持先抬后摆，同时让水平转移和关节跟踪有足够时间 |
| 摆动采用“先抬脚—平移—落脚”三段平滑轨迹 | 直接消除摆动初段仍向后扫而脚尖未离地的拖曳机制 |
| 快速直行才进入 FAST_POLICY，转弯/低速/任务阶段回到 CONTACT_WALK | 固定降低 blend 已在最终转向失败，必须用带迟滞的内部分场景调度 |
| 不在本轮重新训练 | 纯 actor 在 Classic 0.50 m/s 已达到约 0.486 m/s，部署覆盖层是首要根因 |
| FAST_POLICY 保留为显式实验功能，但 Floor1 默认关闭 | 30/60/100 N 均只有较高瞬时速度，没有持续净推进；0.35 m/s 自动接管两次在同一走廊区段触发 Nav2 规划/碰撞恢复失败 |
| Floor1 Nav2 与 CONTACT_WALK 统一回 0.20 m/s | 0.35 m/s Nav2 命令在 WBC/助力层被截到 0.20 m/s，改变曲率并破坏任务；统一包络后完整导航抓取重新通过 |
| 最终采用直行新轨迹、转弯旧轨迹的混合调度 | 三段先抬后摆解决直行前足拖曳；恢复历史 35% 摆动转弯轨迹后，弧线门禁和完整任务同时恢复，3 个干净世界均完成抓取 |
| 新增高速 Phase 7，旧 0.20 m/s 候选作为回退而非当前目标 | 用户确认低速才出现前脚拖曳，并要求导航/键盘以高速策略为主、到桌边才进入 CONTACT_WALK 微调 |
| Phase 8 用 Regulated Pure Pursuit 替换 DWB | DWB 基线出现 19 次 `No valid trajectories`，速度中位数仅约 0.05 m/s；RPP 使命令中位数达到 0.50 m/s，实际运动中位数约 0.476 m/s |
| 水平化 SDF 中的 `navigation_laser` | 固定关节折叠后传感器保留 45° 俯角，把地面当障碍；修复后障碍层量程 0.70–1.20 m 内假点由整片降为 0 |
| Floor1 集成导航默认 `finish_after_pick=true` | 该入口到桌后才启动任务，任务服务器捕获的“起点”就是桌边，不能套用独立搬运演示的 1.30 m 返程门禁 |
| 抓取结束采用 0.08 m 抬升并显式站立稳定 2 s | 最终方块实际抬升 0.109 m，机身 z 恢复到 0.296 m，双指 fixed joint 和持续持物目标均保持 |
